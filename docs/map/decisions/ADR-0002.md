# ADR-0002：方案 C：归档裁决自动闭环——插件 LLM 调度 + 候选自动落库 + 权威入册留人工终审

> 状态：accepted

## 背景

- 方案 B 引擎已自治到「入队」（发现→唤醒→门控→机械消化→pending 队列），但**裁决与固化仍靠人工点火**：每次积压需手动 workflow fan-out（2026-09-03 首轮 302 会话 4 波 33 agents），队列边清边长。
- 复盘三问：① 无自动闭环调度 ② 碎片需治理（已机械消化解决）③ 阶段重复（已 --drain 解决）。本 ADR 解决 ①。
- 用户拍板：方案 C（全自动闭环）＋容量扩容＋辅助文档解除硬限（均已完成/本 ADR 后实现）。

## 决策

1. **执行者 = 插件 daemon-loop**（`@dsh-external/dsh-managing-memory`，inject 增 `llm`）：宿主进程内单轮 LLM 四问裁决，非子代理循环——插件天然是 LLM 宿主（ctx.llm 已有），无需外部调度通道。
2. **裁决触发（节流幂等）**：每次 tick 的 `--due` 后检查——pending 队列 ≥ `adjudicateThreshold`（缺省 10）且距上次裁决 ≥ `cooldownMs`（缺省 6h）→ 逐项裁决（最多 `adjudicateBatch` 条/轮，缺省 10）。
3. **四问裁决单轮 prompt**（输入=队列 signals + 会话元数据）：输出 JSON `{verdict: ADD|SKIP, reason, candidates[]}`：
   - **SKIP**（含重复/注入缓存/一次性/宁缺毋滥）→ 引擎 `mark --done` + `dequeue`（自动清队）。
   - **ADD** → 写 `pending/2026-09-03-arb-<sid前8>.md` 候选（同人工裁决格式：主题/要点/四问/拟落点/溯源）。
4. **自动预合并**：ADD 候选文件数 ≥ `mergeThreshold`（缺省 10）→ 一次 LLM prompt 读候选合并同主题 → 写 `pending/_consolidation-draft-<ts>.md`（**拟入册草案**，含目标 notes 小节与高密度条目）。
5. **权威入册 = 人工一键终审**（唯一人工环，对应方案 C「只剩用户终审」）：草案经人确认后才走 write_gate + 写 MEMORY/notes。**自动裁决/候选/草案永远不直接写权威记忆**（含容量分层后 notes 无硬限——语义正确性仍需人）。
6. **观察性**：裁决/预合并每动作写插件自日志（`~\.dsh\super-injector\dsh-managing-memory.log`）；`--status` 健康度段报「待裁 pending / 距上次裁决 / 草案待审」。

## 后果

- 正面：队列常清（裁决自动）；候选自动累积；草案一键入册；机械+规则+LLM+人四层各司其职；历史积压不再累积（每 6h 或阈值自动消化）。
- 副作用/风险：LLM 误判 ADD/SKIP——以「宁缺毋滥」prompt 偏置 + 阈值/冷却可调 + 终审兜底约束（误判最多进 pending/草案，不污染权威库）；每轮少量 LLM token 成本；裁决质量依赖 ctx.llm 路由可用性（不可用→跳过本轮并记日志，不阻塞）。
- 边界：**不自动写权威记忆**；**不删除既有 pending 候选**（只新增）；草案待审期间不重复触发合并。

## 替代方案

- A. 插件 tick 攒提示、由下个 agent 会话手动 workflow 裁决：仍是人工点火（半自动）——弃。
- B. 引擎内嵌确定性规则裁决（signals 关键词打分）：四问是语义判断，规则无法可靠判 ADD/MERGE——弃（机械消化=唯一的规则层，其余归 LLM）。
- C. 全自动入册（裁决+预合并+写 MEMORY/notes 无人环）：绕过人工终审，容量分层后 notes 甚至无门禁兜底，误判会直接污染权威记忆——**否决**，权威入册留人。
- 选定：A 的引擎自治基础 + B 的边界（规则只做机械消化）+ 插件 LLM 裁决 + **权威入册人工一键**。
